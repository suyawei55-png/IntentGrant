## 摘要

Core v2.0 回答的问题是：AI Agent 代替人类执行高后果操作时，如何证明"此刻确实是本人主动想要执行"。它在企业语境（管理控制平面、岗位绑定、硬件端点私钥签名）下给出了完整答案。

消费者语境存在四个 Core v2.0 未覆盖的结构性差异：

1. **表面差异**。消费级 Agent 大量运行在弱表面（无屏或小屏的耳机、眼镜、戒指，以及语音优先的车载与 AIOS 场景）。AP2 对"用户批准 Mandate"的回答是 Trusted Surface——预设了富 UI 客户端；这一前提在弱表面不成立。
2. **语音差异**。"好的，确认"类语音应答不可作为高保障确认证据：2026 年多源实证，5 秒语音样本即可克隆声纹。
3. **判责差异**。消费争议以客服判责与民事诉讼为主，判责依据目前主要是平台单方系统记录——"仅退款"机制 2025 年在全行业落幕，标志着单方判责模式已被行业自我否定；而司法规则（最高人民法院银行卡司法解释）要求主张"授权交易"的一方举证**交易发生时的验证信息**。
4. **设备能力差异**。消费者拒绝为安全硬件统一买单：从无安全边界的通用蓝牙按键到带 SE/TEE 的穿戴设备，机制跨度极大——任何"物理按键 = 高保障"的一刀切声明都是虚标（§5 机制条件化的由来）。

本规范定义 IG-Lite：在 Core v2.0 四层架构之上，为消费者场景定义**披露（Disclosure Object 与呈现承诺）→ 物理确认捕获（challenge 绑定）→ 凭证（Confirm Grant / Access Grant）→ 证据托管（中立 hash 日志）**的完整语义，并以机制条件化的保障等级（LoA）适配从通用蓝牙按键到安全芯片穿戴设备的全谱系消费者硬件。法律轨道采用《电子签名法》第十三条第二款的**约定式可靠电子签名**，产出客服判责级证据链；金融级轨道留待 Enterprise Profile 扩展（Core v2.0 未定义 CA 认证式效力路径，见 §9.1）。

**v0.2 增量（基于 v0.1.1 开源发布版）。** v0.1.1 已具备完整的知情同意证据基座：披露体系（Disclosure Object 与呈现承诺，§3.1–3.2）、物理确认捕获（IntentGrant，§3.3）、凭证模型（Confirm/Access Grant，§4）、送达留痕（D0 渲染留痕，§3.3，审计级）、机制条件化的保障等级（LoA/DCC，§5）、四段判责链（§3.4）与中立 hash 托管（§8）。知情同意的证据由此可归为四个相互独立的要件——充分性（该说的都说了）、完整性（说的没被改）、送达性（确实给了显著查看机会）、意思真实（本人主动同意）：**v0.1.1 覆盖完整性、意思真实与送达性的审计级形态，v0.2 补足充分性、并将送达性从审计级升级至设备签名级**：

- **充分性 → 告知基线 Schema Registry（§6）**：按交易类型将现行法律披露义务机读化为 schema，required 字段由验证端复算完备性——结构不合规的凭证判 invalid。强制力来源不是一闪的倡议，是法源本身（不合规披露本来就该被排除在有效证据之外）；基线的合法性来源是法源翻译，不是自设标准。
- **送达性 → Delivery Receipt / Transit Fidelity Receipt（§4.7）**：弱表面送达回执（D1，"给了显著的查看机会"的程序语义）与中转保真回执（D2，三段链证明中转方未偷换披露内容），覆盖"存储版本 ≠ 显示版本"的缺口。
- **组合语义**：完整证据链一句话——**该说的都说了、说了的没被改、改不了的确实给了看的机会、看到的被本人授权了**（§6.1 四要件模型）。

生态位：IG-Lite 消费 A2A 任务协议的 **auth-required 状态**并定义其捕获语义；与 AP2 **组合**（Confirm Grant 引用 Checkout Mandate 的 checkout_hash）；术语对齐 FIDO UP/UV 原语。支付通道不在本规范范围内（§1.4 原则一「不动钱」）。

## 1. 概述与范围

### 1.1 问题陈述

消费者语境下，Agent 发起高后果动作（下单、删除、外发、订阅变更、空间设备操作）时的"知情同意"捕获，当前存在五个无法互相补救的缺口：

- **缺口一：富 UI 确认在弱表面不可用。** AP2 的 Mandate Delegation 要求用户在 Trusted Surface 上批准 [S2]；耳机、眼镜、戒指、车载语音没有可点击的富 UI。A2A 任务生命周期已定义 `auth-required` 状态 [S1]，但对"进入该状态后确认动作由谁捕获、以什么保障等级捕获、确认产出什么凭证"没有规定。
- **缺口二：语音确认不可采信。** 声纹克隆已进入低成本黑灰产阶段：5 秒语音样本即可克隆 [S20]。"用户说了'确认'"无法作为高保障证据——这不是产品缺陷，是攻击面。
- **缺口三：判责依据单方化。** Agent 代购等争议中，"用户是否知情同意"只能查平台自己的日志：主张授权方与证据持有方同体（自证陷阱）。"仅退款"（平台单方判定退款）2021 年由拼多多首创、2025-04-22 淘宝与抖音同日全面取消 [S35]——单方判责模式在争议量大时系统性失衡，已被行业自我否定。
- **缺口四：消费者设备能力跨度极大。** 从无安全边界的通用蓝牙按键，到带 SE/TEE 的穿戴设备，安全机制完全不同。任何"物理按键=高保障"的一刀切声明都是虚标。
- **缺口五（v0.2 补全）：告知充分性与送达性无证据化路径。** 平台的披露"说没说全"由谁判定、"给没给查看机会"如何证明，当前只有平台自证日志——自动续费争议中"极不明显的灰色小字体＋默认勾选"被法院认定侵害知情权（2025-08 广州互联网法院案 [S46]），事后审查成本高且不确定；schema 化与送达回执把这两环从事后审查前移到凭证结构层。

### 1.2 Consumer Profile 的定位（与 Core 的分工）

**Core v2.0**（Enterprise Profile）：四层架构（激活层 Layer 0 / 物理动作层 Layer 1 / 凭证层 Layer 2 / 审计层 Layer 3）；企业管理员控制平面；生物绑定与挂失流程；端点私钥签名（量产设计由 SE 芯片片内完成，Core 第 12 章）。金融级 CA 认证式电子签名轨道为**未来扩展，Core v2.0 未定义**（§9.1）。

**IG-Lite v0.2**（本规范，Consumer Profile）：继承四层架构与凭证/审计模型，在消费者语境完成六项重定义：

| 维度 | Core v2.0 | IG-Lite v0.2 | 条款 |
| --- | --- | --- | --- |
| 控制平面 | 企业管理员 | 控制端应用 + 用户本人（无管理员复核路径） | §7.4 |
| 同意的可验证性 | 凭证本身 | 披露先行：Disclosure Object + 呈现承诺 + 时序绑定 | §3 |
| 告知充分性 | 未定义 | 告知基线 Schema Registry（法源机读化） | §6 |
| 送达性 | 未定义 | Delivery / Transit Fidelity Receipt | §4.7、§5.6 |
| 保障等级 | 隐含于风险分级 | 机制条件化 LoA × 设备能力分级 DCC | §5 |
| 证据归属 | 企业侧审计日志 | 中立第三方托管 hash 日志 + 中国法锚点 | §8、§9 |

一句话定位：**Core 回答"操作者此刻是否主动授权"的企业级答案；IG-Lite 给出同一问题在消费者语境的答案——客服判责级证据链。**

### 1.3 场景支柱（示例性，规范不限于）

**P1 随身意图确权**：可穿戴设备 / AIOS 主动服务的高后果确认。Agent 从"生成"走向"代执行"（提醒转下单、日程变更确认、空间设备操作）时，捕获"本人此刻要"的物理证据。

**P2 个人数据与记忆访问授权**：Agent 访问用户日程、笔记、健康等个人数据前，通过 Access Grant 获得带约束的常授权（范围、配额、可撤销），并按 §5 的 LoA 规则决定哪些动作需要逐次确认。

**P3 商业交易披露确认**：即时零售 / Agent 代购的下单确认。披露（商家、品项、数额、时效）→ 物理确认 → 四段判责链 → 争议时的证据裁决。本支柱与 AP2 Checkout Mandate 组合（§2.3）。

### 1.4 设计原则

1. **不动钱**：支付授权与清算走平台既有支付能力 / AP2 Payment Mandate [S3]；IG-Lite 只捕获"同意时刻"（含金额知悉），不触碰支付通道、不经手支付凭证。
2. **机制条件化**：LoA 是机制属性不是标签（§5）；设备能力声明必须诚实（§7.2），声明与实际不符即违规（虚标禁令，第 12 章）。
3. **披露先于确认**：没有可验证披露的确认不构成知情同意（§3）；确认动作本身必须有防疲劳与防误触设计（§10.1）。
4. **证据分层留存**：hash 链永久（非个人数据）+ 披露原文限时（N 参数）+ 争议冻结（"停止处理"语义，§9.4）——留痕与删除权的张力用机制消解，不是宣传话术。
5. **生态位组合不替代**：挂在 A2A 状态、AP2 mandate、FIDO 术语与既有中国法条上；不宣称替代任何既有标准，不宣称未验证的互操作性。
6. **法源翻译不发明（v0.2 新增）**：告知基线（§6）的每一条 required 字段**必须**挂现行法源（条文号＋施行日期）；无公开法源支撑的字段不得进 required——协议翻译义务，不创设义务（§6.3）。

### 1.5 规范用语与术语约定

- **必须（MUST）**／**禁止（MUST NOT）**：规范的强制要求；不符合即不构成符合本规范的实现。
- **应当（SHOULD）**：推荐要求，存在已知理由才可偏离，且偏离必须可说明。
- **可以（MAY）**：可选行为。
- 术语与 Core v2.0 术语体系一致：**物理授权端点（PAE）**——承载物理确认动作的硬件端点（形态不限）；**控制端应用（Controller）**——管理 PAE 绑定、组装与送签凭证的应用；**控制平面**——企业管理侧的管理控制面（消费者语境由控制端应用承担，§7.4）。本 Profile 新增术语见附录 A。
- **编号消歧（v0.2.1）**：本规范中 L0–L3 一律指 §5 保障等级（LoA）；Core 四层架构一律以层名指称——激活层（Layer 0）/ 物理动作层（Layer 1）/ 凭证层（Layer 2）/ 审计层（Layer 3）。两套编号无对应关系，历史上曾共用 L 前缀，v0.2.1 起架构层不再使用 L 简写。
- 引用标记 [S#] 对应文末「信源清单」；法条引用以现行有效文本为准。

### 2.2 A2A：auth-required 的语义与捕获

A2A（Linux 基金会托管）任务生命周期七态中已存在 `auth-required` 状态 [S1]；该状态的语义与捕获未定义。IG-Lite 填补三件事：

1. **捕获路由**：任务进入 auth-required 后，确认请求由 AIOS 路由到可用 PAE（§7.3）；
2. **凭证语义**：确认产出 Confirm Grant（§4.2），其 LoA 与证据归属按本规范定义；
3. **状态退出**：Grant 签发并消费后任务恢复执行；Grant 过期或被拒，任务按 A2A 语义失败或取消。

当消费任务模型不采用 A2A 生命周期（如 MCP 工具调用、平台结算流）时，本规范定义 **confirm-required** 状态作为等价入口：Agent 在执行高后果动作前进入该状态，其捕获语义（路由 §7.3、披露 §3、物理确认 §10.1、凭证产出 §4）与 auth-required 一致。

### 2.3 AP2：商业切片组合

AP2（2025-09 发布，2026-04 捐赠 FIDO 联盟 Agentic Authentication 技术工作组 [S4]）定义了基于 W3C VC 的 Mandates：closed / open Checkout Mandate 与 Payment Mandate [S3]。关系判定：**不是竞争，是组合**。

- AP2 的 Mandate Delegation 发生在 Trusted Surface [S2]；弱表面场景（耳机/AIOS 无屏可点）AP2 未回答——IG-Lite 给表面分级：Trusted Surface 为强表面，弱表面走本规范的披露承诺与物理捕获。
- **组合语法**：Confirm Grant 的 `mandate_ref` 字段引用 closed Checkout Mandate 的 `checkout_hash`（SD-JWT VC，vct=mandate.checkout.1）；Access Grant 的约束语法对齐 open Checkout Mandate（allowed_merchants / line_items / quota）[S3]。
- **措辞纪律**：本规范只宣称**语义兼容、字段可映射**，不宣称可互操作——AP2 生态不认识 IG-Lite，真互操作是后续版本的生态工程。
- AP2 原文以 NOTE 将 "a directly trusted user key, such as a passkey or hardware-attested key" 列为**未来可探索**的 Mandate 委托信任模型（现行定义仅为 User Credential 与 Trusted Agent Provider 两类）[S2]——PAE 即该未来方向（硬件证明密钥路径）的一种实例化。此处引用如实标注其探索性质。

### 2.4 MCP elicitation：正交

MCP elicitation（2025-06-18 规范版）是服务端向客户端请求**结构化输入**（JSON Schema 表单，三态响应）[S5]，自述不强制任何用户交互模型，且 MUST NOT 用于请求敏感信息。定性：**MCP 解决"Agent 向用户要参数"，IG-Lite 解决"用户向 Agent 给同意"**——正交互补，无冲突。

IG-Lite 的 MCP 工具层映射以独立文档《IntentGrant MCP Server 接口定义 v0.1》承载，不在本规范内定义——**本规范保持传输层中立**：MCP 是绑定层不是协议层，规范文本不因某一绑定形态而特化（接口定义文档与本规范的版本关系见 §13.1）。

### 2.5 FIDO：术语对齐

- PAE 物理事件引用 FIDO **User Presence（UP）** 概念；Core 激活层的生物核验对应 **User Verification（UV）**；DCC 分级与能力声明（§5.1、§7.2）借用 authenticator attestation 能力声明的表述方式 [S6][S7]。
- 一处刻意差异：CTAP2.3 允许单次触摸构成 UP [S6]；IG-Lite 捕获的是**同意信号**而非在场信号，单击不构成同意（§10.1.1）。差异理由与先例坐标系见 §10.1.1。
- FIDO Agentic Authentication TWG（2026-04-28 成立 [S4]）议程覆盖"用户如何向 Agent 委托动作"的认证保障；IG-Lite 是该议程在中文 AIOS 与中国法语境下的先行答案，发布后向其提交评论意见。

### 2.6 OAuth 族（继承 Core）

Core v2.0 第 2 章与 RFC 9396（RAR）、RFC 8693/9449/8705 的对齐关系全部继承；IG-Lite 的 Grant 结构在其上追加披露与 LoA 语义，不改变 Core 的对齐结论。

### 2.7 国内标准生态位

国内智能体标准体系正在成形：政策层，《智能体规范应用与创新发展实施意见》（2026-05）要求建立智能体标准体系 [S43]；强制性国家标准《智能体应用安全基本要求》已立项（计划号 20263116-Q-252，2026-07 下达，全球首部智能体安全强标）[S41]；智能体身份管理方向的国标亦有立项报道 [S44]。团体标准层面，《智能体身份鉴别与授权技术框架》《智能体运行时安全技术要求》由中国网络空间安全协会提出、蚂蚁集团联合研究院所、运营商、互联网厂商等单位参与编制，2026-09-09 于外滩大会正式启动 [S42]。

生态位判定（截至本规范发布日）：上述布局覆盖智能体自身的身份鉴别、权限管控、运行时安全与应用安全基线；**确认时刻的披露语义与判责证据留存**（本规范 §3、§4、§6、§8、§9）在公开标准文本中尚无对应覆盖。定性同本章各节：**正交且可组合**——身份鉴别回答"Agent 是谁、权限几何"，本规范回答"人类同意时刻如何被可信捕获与留存"；运行时安全技术不定义证据法锚点，本规范不触及智能体自身安全。发布后，以对 FIDO AA TWG 的同样方式（§2.5）向国内标准起草方提交对照意见与评论。**v0.2 补充**：消费者权益保护方向的现行法披露义务（《消保条例》§10、《网络交易监督管理办法》§18、《电商法》§17 等）是本规范 §6 告知基线的直接法源——国内生态位从"无人覆盖"延伸为"翻译现行法"（§6.6 法源映射）。

## 3. 披露与意图捕获

> 本章为 Core v2.0 第 4–6 章（激活层 / 物理动作层 / 凭证层）在消费者语境的语义扩展：Core 定义"物理事件如何变成凭证"，本章定义"凭证之前的知情如何成立"。v0.2 起，本章另承担与 §6 告知基线的衔接：Disclosure Object 新增 `schema_ref` 字段（§3.1）。

### 3.1 Disclosure Object（披露对象）

Agent 请求确认前**必须**构造 Disclosure Object 并完成呈现。最小字段：

```json
{
  "do_id": "do_01hv3k9x2q8c4rm7m3w2e6k9zm",
  "schema_ref": "ig:disclosure:T-0@1.0.0",
  "context_template": "将向{merchant}下单：{item}（{attrs}）x{qty}，合计{amount}，{eta}",
  "rendered": "将向示例咖啡下单：美式咖啡（去冰）x1，合计16.90元，约15分钟送达",
  "scope": "commerce.order.create",
  "counterparty": "示例咖啡（示例商户）",
  "amount": { "value": "16.90", "currency": "CNY" },
  "attrs": { "item": "美式咖啡", "qty": 1, "ice": "去冰" },
  "risks": ["现制饮品不支持七日无理由退货"],
  "sensitive": false,
  "loa_target": "L1.5",
  "delivery_tier": "D0",
  "confirm_window": 60,
  "issued_at": "2026-09-12T10:29:00+08:00",
  "evidence_rules_version": "h(b64url)…",
  "disclosure_hash": "b64url(SHA-256(canonical_json))"
}
```

- `do_id`：披露对象唯一标识，**必须**由 ≥128bit CSPRNG 生成（UUIDv4 / ULID-26），并作为 hash 计算输入的一部分。作用：披露核心字段是低熵组合空间（商户 × 品项 × 数额 × 属性可被枚举），若 hash 输入不含高熵随机量，公开托管日志（§8 准入审计）上的 `disclosure_hash` 可经字典枚举重建交易内容——"hash 非个人数据"的定性（§9.3）将失去密码学支撑。`do_id` 入 hash 后，枚举在计算上不可行。
- `schema_ref`（v0.2 新增）：本披露适用的告知基线 schema 标识（含版本号，`ig:disclosure:<类型>@<版本>`）。**应当**填写；填写后验证端按该 schema 复算 required 完备性（§6.3 强制力链），未按 schema 提供完备 required 字段的凭证判 invalid。schema 的类型选择与类型注册表见 §6.4。
- `disclosure_hash` 的计算对象为**核心字段**（do_id、schema_ref（若存在）、scope、counterparty、amount、attrs、risks、sensitive、loa_target、delivery_tier、evidence_rules_version）的规范化 JSON；规范化必须遵循 RFC 8785（JCS）[S15]——这是跨设备 hash 一致的基础。`do_id` **不得**出现在公开托管日志中（§8）。
- 涉及健康等**敏感个人信息**的场景（P2），Disclosure Object **必须**置 `"sensitive": true`，并触发个保法 §29 单独同意语义（法条映射见 §9.2）。
- `evidence_rules_version`：本披露所援引平台证据规则（用户协议约定的可靠电子签名条件，§9.1）的版本 hash，用于防止"平台单方修订规则导致既有证据指向漂移"。
- `delivery_tier`（v0.2 新增）：本披露的送达证明等级声明（D0/D1/D2，§5.6），入 hash 防降级改写；与 §5.6 类型默认组合及 §6.4 schema 输出联动。
- `rendered` 是弱表面实际呈现的文本（播报稿/屏显内容），**必须**与核心字段语义一致；渲染留痕见 §3.3。
- 非交易场景的映射：P2 数据访问场景 `counterparty`=数据源、`amount` 替换为 `rate`（速率限额）；P1 意图场景 `amount`/`counterparty` 按动作语义替换（如目标设备名+操作）。核心字段结构不变。

### 3.2 呈现承诺（Presentation Commitment）

弱表面（语音播报、≤1 英寸屏）向用户呈现绑定信息时，**必须**为以下二者之一：

- **a) 跨面尾码核对**：可信呈现面（控制端应用屏幕，或配对的第二设备屏）显示完整披露与 `disclosure_hash` 的**尾 8 位 hex**；弱表面播报同一尾码；用户比对两处一致。本模式**必须**存在独立于播报通道的第二可信呈现面，否则不得使用。第二可信呈现面宜与弱表面**宿主隔离**（不同设备）：仅通道隔离而渲染控制方同体（如同一眼镜/同一手机同时渲染投射与播报）的配置，尾码仅具注意力绑定语义，不得宣称跨面完整性校验（判定口径与 §11.1 一致）。其语义与 Microsoft Authenticator 的 number matching 一致：把用户注意力**绑定到可信面内容**上（对 MFA 疲劳轰炸的官方对策 [S23]）。
- **b) 结构化三元组**：关键数额（或速率限额，**含币种**或由行业 Profile 声明单一币种）+ 对方主体名 + `disclosure_hash` 尾 4 位（口头参考码），由弱表面播报。三元组承载交易语义本身——用户听到的内容即所签内容的核心要素，按键即对该内容同意。

**禁止**在弱表面仅播报裸尾码（任何位数）而不满足 a) 的第二可信面要求或 b) 的结构化内容。

理由：用户无法心算 SHA-256——任何尾码在**单一**弱表面上都不构成用户可独立校验的密码学绑定。尾码的验证语义只能是**跨面比对**（a）；单面场景下，唯一承载语义的是**内容本身**（b）。尾码防御的目标是"无注意力盲批"（疲劳攻击面）；"播报内容与签署内容不符"由 审计层渲染留痕与核心字段的事后审计一致性比对捕获（§3.1、§4.5）。a) 的残余风险：尾 8 位 = 32bit 抗碰撞，GPU 离线枚举分钟级可行——其安全前提是第二呈现面与 challenge 签发方不同时沦陷（§11.1）。

### 3.3 捕获时序（Timing Binding）

- PAE 签名**必须**绑定实时 challenge：`nonce + disclosure_hash + 过期时间`；确认窗口默认 ≤60 秒。
- **未收到 challenge 的物理事件不产生 Grant**：离线按键丢弃，不缓存不转发（缓存转发+降级标记为后续版本可配置项）。
- 审计层验证时序：物理事件时间戳**必须**晚于披露播报开始、早于 challenge 过期。
- **渲染留痕（D0，双模态证据的当前边界）**：本机制即 §5.6 送达等级中的 **D0**——渲染方自证的审计级留痕。播报文本 hash 入审计层日志（**必须**；播报文本属披露原文，留存受 §9.3 N 参数约束，N 到期后仅存其 hash）；TTS 音轨 hash 入审计层日志（交互含音频播报通道时**必须**，纯屏幕交互豁免）。二者验证语义不同：**播报文本 hash 承担与签署披露的一致性比对**（§3.1/§4.5 事后审计锚点）；**音轨 hash 仅承担"播报事实与时序"的单次性留痕**——音频字节流不可复现，不承担一致性语义。将规范化播报稿纳入 Grant 签名对象（签署级音频绑定）为后续议题（§11.2）。审计层的 ≥6 个月下限适用于审计索引与 hash 链等机制数据，不含披露原文。v0.2 的 D1/D2（§4.7）将送达证明从 D0 的自证级升级为设备签名级。
- 播报-按键窗口配对（§10.1.3）：播报完成后 ≤60 秒内按键有效；**播报进行中按键无效**（静默期，防"未听完先按键"的锚定式滑过）。

信息性：完整确认消息时序（happy path，v0.2 含送达回执）——

```
Agent → 控制端应用: ConfirmationRequest(scope, counterparty, amount, attrs…)
控制端应用: 构造 Disclosure Object（含 do_id/schema_ref/disclosure_hash）
             → 按schema_ref复算required完备性（§6.3，缺字段=不出challenge）
             → 渲染留痕入审计层 → disclosure_hash 提交托管方
控制端应用 → 弱表面: 播报 rendered + 绑定信息（§3.2 a/b）
控制端应用/渲染方: 生成送达回执 D1/D2（§4.7，按 delivery_tier）
控制端应用 → PAE: challenge{nonce, disclosure_hash, exp}
用户 → PAE: 确认动作（双击/长按，§10.1.1）
PAE → 控制端应用: 事件签名（按 attested_by 主体，§4.2 签名规则）
控制端应用: 验签 → 签发 Confirm Grant → Agent 消费凭证 → 执行
执行方 → 控制端应用: Receipt{executed_action_hash} → 对齐校验 → receipted / VIOLATED
```

### 3.4 判责链（四段 hash 链）

```
意图捕获（Disclosure Object 签发）
   → 披露（呈现承诺 + 渲染留痕[D0] / 送达回执[D1/D2]）
   → 确认（PAE 物理事件签名）
   → 执行（回执 hash 对齐，§4.5）
```

四段各自签名衔接，**禁止**合并为单一总 hash。

词汇对照：摘要中的四功能段（披露 → 物理确认捕获 → 凭证 → 证据托管）即本链的功能视角——「凭证」为「确认」段产出的 Grant，「证据托管」对象为各段 hash（§8）与「执行」段对齐后的证据对象。

理由：《人民法院在线诉讼规则》对区块链存证"上链后推定真实、上链前数据真实性另行审查" [S31]；《最高人民法院民事证据规定》§93 将真实性判断落在生成/存储/传输所依赖系统环境的完整性可靠性 [S30]。链式存证只保"上链后"，**上链前链路必须分段独立可查**——这是四段不可减为一段总 hash 的证据法依据。

### 3.5 信道与配对安全（激活层绑定的 Profile 增量）

**配对关联模型**：

- 激活层绑定**必须**使用 LE Secure Connections（ECDH P-256）；关联模型**必须**为 Numeric Comparison（双端比对六位数字）或 OOB（如扫码）。
- Just Works 仅允许无屏设备兜底路径；经 JW 绑定的设备，其 Grant 的 LoA **永久封顶 L1**（JW 的 TK=0 级保护、无 MITM 防护——Nordic 与 TI 官方文档原文确认 [S17][S18]）。
- **绑定事实的记录义务（Profile 增量）**：实际采用的关联模型**必须**记录于 激活层绑定记录的 Profile 增量字段 `association_model`（取值 `numeric_comparison` / `oob` / `just_works`），并收录入 §7.3 注册表快照——「经 JW 绑定」的 LoA 封顶判定以该记录为证据；注册表条目缺失该字段时，按 `just_works`（最不利模型）处理。
- **绑定后复核**：无屏 PAE 走 JW 兜底时，首次 Grant 签发前**必须**完成人工复核——控制端应用展示设备指纹（序列号/公钥尾码），用户确认"这就是我手上的设备"。

**事件签名与利益冲突**：

- **L2 及以上**证据的物理事件**必须**由 PAE 设备端密钥对 challenge 签名产生（`attested_by: "device"`）；应用自证签名（`attested_by: "app"`）的凭证**封顶 L1.5**。
- DCC-C 设备（§5.1）的签名实际发生在控制端应用（手机既是 BLE 中枢又是被授权方）：此类签名**必须**在 审计层记录中标注 `attested_by: "app"`（应用自证），与 `attested_by: "device"`（设备自证）严格区分——表述方式对齐 FIDO authenticator attestation 能力声明 [S7]。

**中继（Relay）**：

- 主缓解 = §3.3 的 challenge-response 时序绑定：中继者无法应答实时 challenge，只能转发过时签名（过时 = 无效）。
- **邻近性不得作为安全属性依赖**（车钥匙 relay 先例：攻击者在受害者数米内即可中继解锁，Tesla 以 UWB 测距应对 [S19]）；UWB 精确测距列为后续版本可选增强（对齐 CCC Digital Key 路径）。

## 4. 凭证模型

### 4.1 凭证类型总览

| 凭证 | 语义 | 消费方式 | 对应 Core |
| --- | --- | --- | --- |
| **Confirm Grant** | 一次性确认："本人此刻同意这一次" | 单次消费，默认 ≤300 秒过期 | Core 凭证层 Grant（操作级）的消费者细化 |
| **Access Grant** | 带约束常授权："这类事可以，边界如下" | 常设，配额内免逐次确认 | Core Permission_Scope 的扩展 |
| **Receipt**（§4.5） | 执行回执：执行了什么、与披露是否对齐 | 每次执行产出 | Core 审计层 Result 的结构化 |
| **Delivery Receipt**（§4.7，v0.2） | 送达回执：弱表面确实渲染了披露（D1） | 每次披露送达产出（按 delivery_tier） | Core 无对应——本 Profile v0.2 新增 |
| **Transit Fidelity Receipt**（§4.7，v0.2） | 中转保真回执：中转渲染与源披露一致（D2） | 每次中转渲染产出（按 delivery_tier） | Core 无对应——本 Profile v0.2 新增 |

**边界规则**：不可逆动作（记忆删除、外发、注销类）**永远不**被 Access Grant 覆盖——每次都需要 Confirm Grant（§10.2 场景表）。**送达回执不承载同意语义**：D1/D2 中的任何字段、任何用户行为痕迹均不构成 §10.1.1 意义上的同意信号；同意唯一由 IntentGrant（Confirm Grant）承载（§4.7）。

### 4.2 Confirm Grant

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `grant_id` | UUID | 沿用 Core `Grant_ID`，全局唯一 |
| `grant_type` | `"confirm"` | 一次性确认凭证 |
| `pae_id` | String | 沿用 Core `Device_ID` |
| `dcc_class` | `"A" / "B" / "C"` | §5.1 设备能力分级 |
| `attested_by` | `"device" / "app"` | §3.5 事件签名主体 |
| `disclosure_hash` | String | 绑定的 Disclosure Object hash（§3.1） |
| `schema_ref` | String（可选） | 与 Disclosure Object 同源（§3.1/§6.4）；存在时验证端按其复算完备性（§6.3） |
| `delivery_receipt_ref` | Object（可选） | 送达回执引用（§4.7）：`{receipt_type, receipt_id}`，高价值交易判责链含送达段 |
| `mandate_ref` | Object（可选） | §2.3：引用 AP2 closed Checkout Mandate |
| `loa_target` | `"L1" / "L1.5" / "L2"` | 目标保障等级；实际 LoA 低于目标 → Grant 无效（§5.3） |
| `confirm_modality` | `"double_click" / "long_press" / "declared_equivalent"` | §10.1.1 动作模式；无障碍替代必须声明（§5.5） |
| `challenge` | Object | `{nonce, disclosure_hash, issued_at, expires_at}`，§3.3 |
| `evidence_rules_version` | String | 与 Disclosure Object 同源 |
| `session_ref` | UUID | 归属会话（频控计数用，§10.1.2） |
| `issue_time` / `expire_time` | Timestamp | 单次消费；默认 ≤300 秒（对齐 Core High 档） |
| `signature` | String | PAE 密钥签名（按 `attested_by` 主体） |

**签名计算对象（规范要求）**：

- `signature` 覆盖本凭证**除 `signature` 外全部字段**（含 `challenge`）的 RFC 8785（JCS）规范化字节串 [S15]。仅对 challenge 签名不足以覆盖凭证本体：若设备只签 challenge，控制端应用可在设备签名之外组装任意 Grant 字段，设备端签名的防伪造意义即落空。
- `attested_by: "device"` 时，该签名**必须由 PAE 设备端计算**——控制端应用组装凭证草稿后经激活层通道送签，设备返回 `signature`；应用**不得代签**（DCC-C 场景即 `attested_by: "app"`，§3.5）。
- 验证公钥随凭证分发：Grant 副本**应当**内嵌 PAE 公钥或其指纹，使争议时的验证方（平台/司法/用户）无需回连控制端注册表即可独立验签；密钥轮换经 Core v2.0 激活层重绑定流程。

**签发前置校验（v0.2 增补，required fail 分支）**：控制端应用组装凭证草稿前**必须**校验 Disclosure Object 与 `schema_ref` 的一致性——若 `schema_ref` 存在，按 §6.3 复算 required 完备性：**缺失、空串、仅空白、或 not_applicable 声明缺失理由 → 拒绝生成 challenge（交易在协议层走不到确认环节）**。该校验防的是"无意不合规"（开发者漏字段）；对有意绕过者，防线在验证端仲裁与法律端——**两层各防一类对象，协议层不得宣称"准入拦截"**（§6.3 生态定位边界）。

示例（P3 商业交易支柱，与 §3.1 示例同一笔订单）：

```json
{
  "grant_id": "urn:uuid:0d1f9a4c-…",
  "grant_type": "confirm",
  "pae_id": "PAE-2026-0001",
  "dcc_class": "B",
  "attested_by": "device",
  "disclosure_hash": "b64url(SHA-256(JCS(§3.1 核心字段，含 do_id)))",
  "schema_ref": "ig:disclosure:T-0@1.0.0",
  "delivery_receipt_ref": {"receipt_type": "delivery", "receipt_id": "urn:uuid:…"},
  "mandate_ref": {
    "protocol": "ap2",

    "checkout_hash": "b64url(SHA256(checkout_jwt))"
  },
  "loa_target": "L1.5",
  "confirm_modality": "double_click",
  "challenge": { "nonce": "9f3a…", "disclosure_hash": "（同上）", "issued_at": "…", "expires_at": "…+60s" },
```

### 4.3 Access Grant

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `grant_id` / `pae_id` / `dcc_class` / `attested_by` | 同 Confirm | — |
| `grant_type` | `"access"` | 常授权凭证 |
| `scope_constraints` | Object | 约束语法对齐 AP2 open Checkout Mandate [S3] |
| `per_action_policy` | Object | 逐动作 LoA 路由（见下） |
| `quota` | Object | 频率与金额限额（§10.1.2 复用） |
| `validity` | Object | `{not_before, not_after, renewal}`；常设或会话级 |
| `revocation` | Object | 挂失/撤销对齐 Core 第 10 章应急流程 |
| `signature` | String | 签名规则同 §4.2：覆盖本凭证除 `signature` 外全部字段的 JCS 规范化签名，按 `attested_by` 主体计算（`attested_by: "device"` 时须设备端计算）——防止应用侧组装后篡改配额与约束 |

`scope_constraints` 示例（P3，语义对齐 open mandate 字段名）：

```json
{
  "allowed_actions": ["commerce.order.create"],
  "allowed_merchants": ["示例咖啡"],
  "line_items": [ { "category": "现制饮品", "max_qty_per_order": 3 } ],
  "per_order_amount_max": "30.00",
  "data_retention": "session_only"
}
```

`per_action_policy` 示例（P2，数据访问）：

```json
{
  "default": { "loa": "L1", "quota": { "calls_per_hour": 20 } },
  "escalate": [
    { "action": "memory.read.recent_7d", "loa": "L1" },
    { "action": "memory.export", "loa": "L2", "grant": "confirm" },
    { "action": "memory.delete", "grant": "confirm_always" }
  ]
}
```

- `grant: "confirm_always"` = 永远需要 Confirm Grant（不可逆动作，§4.1 边界规则）。
- Access Grant 签发本身**必须**经过一次完整 Confirm 流程（含披露与物理确认）；配额用尽或策略升级时**必须**回到逐次确认。
- 该 Confirm 流程的 Disclosure Object **应当**完整呈现将被常授权的约束（scope、配额、限额）——约束语义由此进入披露 hash 与判责链（§3.4），事后可对账。

### 4.4 生命周期与状态机

```
drafted（披露构造）
  → presented（呈现承诺执行，渲染留痕[D0] / 送达回执[D1/D2]）
  → challenge_issued（≤60s 窗口）
  → confirmed（物理事件签名有效 → Grant 签发）
      → consumed（单次消费，执行触发）
      → receipted（回执 hash 对齐，闭环）
  / expired（窗口或凭证过期）
  / revoked（挂失/撤销，对齐 Core 第 10 章）
  / rejected_bind（激活层核验失败，对齐 Core 第 8 章）
  / rejected_schema（required 完备性校验失败，v0.2 新增——凭证不出，交易不走）
```

状态语义参考 Microsoft Agent Governance 的意图生命周期（Declare → Approve → Execute；官方博客 2026-05-14《Governance at the Speed of Agents》已核实）；本规范将终态细化为 `receipted` / **VIOLATED（越权执行）**（其中 hash 不对齐记为 VIOLATED，见 §4.5）；v0.2 新增前置态 `rejected_schema`（§6.3）。

### 4.5 执行回执与 TOCTOU 对齐

确认了 X、执行了 Y 的间隙（TOCTOU）必须闭合：

- 执行方完成动作后**必须**产出 Receipt：`{grant_id, executed_action_hash, disclosure_hash, executed_at, result}`；
- `executed_action_hash` **必须**与 `disclosure_hash` 所声明 scope 的对齐规则匹配（动作、主体、数额/限额在容差内一致）；
- **不对齐 = 凭证链不为其提供授权证明**：该执行在审计层记录为越权执行（VIOLATED）。本条仅判定证据链层面——**不判定合同效力**：合同成立与否依《电子商务法》§48 与《民法典》§491 另行判断（§9.2）。
- 模式印证：AP2 Action Authorization 的 Verifier 返回 Receipt [S2]；IG-Lite 把"回执对齐"从支付域推广到全部确认场景。

### 4.6 设计理由：跨设备 WYSIWYS（信息性）

硬件钱包的显示完整性金标准是 WYSIWYS——安全屏直连安全芯片，"所见即所签"（Ledger/Trezor 官方表述 [S10][S11]）。但 Ledger 的完整性靠**一体化硬件**解决；AIOS 场景是跨设备的（渲染在 AIOS/控制端，签署在 PAE），没有一体化硬件。

IG-Lite 的解法是**时序绑定 + 第三方托管**：披露 hash 在物理事件之前生成并经独立通道（托管方，§8）留痕；签署的 Grant 绑定该 hash；审计层验证"事件晚于播报、早于 challenge 过期"的时序。"确认了什么"不由签署设备自证，由**披露-签署时序 + 第三方托管**共同证明。这是本规范相对既有先例的技术增量，也是"耳机小屏/无屏如何防误导"的答案。

### 4.7 Delivery Receipt 与 Transit Fidelity Receipt（v0.2 新增）

> 本节定义两种送达证明凭证，对应 §5.6 的 D1/D2 等级。两者证明对象不同，**不可互换引用**。设计上游：设计稿《DisplayReceipt 送达回执与中转保真》（2026-09-16）＋ red-team 修订（2026-09-20，redteam/模拟评审-v0.2-2026-09-20.md）。

#### 4.7.1 模式 A：弱表面送达回执（Delivery Receipt, D1）

**语义**：证明**该配对设备的弱表面在窗口内渲染了绑定内容的完整披露**。不证明：用户已读、看懂、在场、同意（《消保条例》"显著方式"止于机会；同意唯一由 IntentGrant 承载）。

**停留时长的证明力按设备能力分层（red-team E-2/P-2 修订）**：设备签名证明的是签名时点与签名对象，不能证明"渲染持续了 N 秒"——自报时长若直接入证明对象，先被质疑的是"渲染 1 秒签成 8 秒"。两条路径：

- **安全时间源路径**：DCC 端点能力矩阵含"安全时钟"能力位（§5.1，TEE 保护区时钟）；具备该能力的端点，render_start/end 双时戳由安全时钟产生，纳入证明对象（"停留规范时长"的程序语义成立）；
- **claimed 路径**：无安全时间源的端点，`render_duration_ms` 为 **claimed 字段**（渲染端自报、参与 hash 防篡改但不参与证明），证明对象收窄为"渲染事件于窗口内发生"。

**凭证结构（示意）**：

```json
{
  "receipt_type": "delivery",
  "receipt_id": "urn:uuid:…",
  "device_id_cert": "…(DCC-B 以上设备证书链)",
  "grant_ref": "urn:uuid:… | null",
  "content_hash": "b64url(SHA-256(canonical_json(rendered_disclosure) || per_receipt_nonce))",
  "nonce": "…(≥128bit 设备 CSPRNG，入凭证)",
  "schema_ref": "ig:disclosure:T-SUB@…(与 Schema Registry 对齐)",
  "render_start": "2026-…T…Z",
  "render_duration_ms": 8000,
  "signature": "…(设备私钥，TEE/SE 片内)"
}
```

- `grant_ref` **可空**：播报型先播报后确认、浏览后未确认时为 null。空值语义＝"披露送达但确认未发生"——恰为"送达回执不承载同意语义"的结构自证。
- **隐私红线（red-team P-1 修订）**：本节全部内容 hash（D1 `content_hash`／D2 `rendered_content_hash`）的计算**必须**混入 per-receipt nonce（设备 CSPRNG，≥128bit），nonce 随凭证存放；托管方**禁止**收录 nonce↔渲染内容的对应关系（与 §3.1 do_id 禁录同构——披露渲染内容低熵，裸 hash 在公开日志下可字典重建交易内容）。
- 签名端点下限 **DCC-B**（§5.1）——DCC-C 无独立安全边界，其签名主体为控制端应用（`attested_by: "app"`），不构成设备签名送达证明；DCC-C 场景的送达证明回落 D0（§3.3 审计级）。

#### 4.7.2 模式 B：中转保真回执（Transit Fidelity Receipt, D2）

**语义**：证明**中转渲染方呈现的内容与源平台生成的披露一致**——覆盖"渲染控制方 ≠ 披露生成方"的全部链路（手机主 Agent 转述平台披露、B 端代理渲染同构适用）。三段链：

```
源披露留痕：源平台生成 source_disclosure_hash + 托管锚（时间戳或完整托管，§8）
   ↓
中转渲染：渲染方按源披露渲染（可转述格式，交易要素逐字保真）
   ↓
渲染回执：渲染方设备签名 rendered_content_hash，fidelity 比对 → match / mismatch
```

**凭证结构（示意）**：

```json
{
  "receipt_type": "transit_fidelity",
  "receipt_id": "urn:uuid:…",
  "device_id_cert": "…(DCC-A/B)",
  "source_disclosure_hash": "b64url(…)(源平台生成)",
  "source_anchor_ref": "…(时间戳或托管留痕引用，§8)",
  "rendered_content_hash": "b64url(… || per_receipt_nonce)(渲染端计算)",
  "render_agent_id": "…(主 Agent 身份，KYA 对接点)",
  "render_timestamp": "…",
  "fidelity_verdict": "match | mismatch",
  "signature": "…(渲染端设备私钥)"
}
```

**边界**：

- 证明对象是**渲染保真**，不是用户已读、不是同意；准不在场场景中，中转保真回执**必须**与 Confirm Grant 组合使用方构成完整证据链（保真＋确认）。
- 渲染即落定：`rendered_content_hash` 针对渲染时点的规范化内容快照（含 per-receipt nonce，见 4.7.1 隐私红线）；渲染后的本地状态变化不在证明域。
- **重渲染版本化（red-team E-3 修订）**：动态内容（库存/价格变动）触发重渲染**必须**重签新 receipt，新 receipt 引用 `prior_receipt_id` 串链；mismatch 后该链状态 VIOLATED，后续披露须新开链；部分字段更新走"增量重渲染＋全量重签"（receipt 无增量结构）。
- **mismatch 仲裁基准（red-team L-5 修订）**：仅可信时间戳路径下，源平台可事后重铸新版本源哈希、把偷换伪装成正常 match——故仲裁**必须**以**渲染时点前最新的托管锚**为基准；仅时间戳路径的回执限审计参考、**不得**作采信级中转保真主张，采信级以完整托管路径（§8）为前提。
- 判责归属：mismatch 时，举证不利方向由链路角色定——中转方持回执、源平台持源哈希，二者对齐失败的责任在改的一方，证据结构天然指向（以上一条仲裁基准为前提）。

#### 4.7.3 能力状态声明

两模式凭证结构为**语义设计**（v0.2 规范定义）；设备签名通道依赖 DCC-B 以上端点（量产安全硬件，§12 实现状态）；源披露留痕对接依赖源平台商务配合（§11.2 保留限制）。**规范目标状态 ≠ 当前实现能力**（第 12 章纪律）。

## 5. 保障等级（LoA）

### 5.1 设备能力分级（DCC）——LoA 的物理前提

| 等级 | 定义 | 示例形态 |
| --- | --- | --- |
| DCC-A | 密钥存储于设备安全边界内（SE/TEE/安全飞地），固件签名验证 | 带安全芯片的戒指/手表 |
| DCC-B | 密钥在设备专用存储，无安全边界 | 高级耳机固件密钥 |
| DCC-C | 密钥在控制端应用/手机层，设备仅上报事件 | 通用蓝牙遥控按键（市售相机遥控器形态） |

DCC 分级是**声明 + 验证**问题：能力声明（§7.2）与实际机制不符 = 虚标，按第 12 章纪律处理。

**能力矩阵扩展（v0.2）**：DCC 分级之外，端点**可以**声明附加能力位，记入能力声明（§7.2）：

| 能力位 | 含义 | 解锁 |
| --- | --- | --- |
| `secure_clock` | TEE/SE 保护区时钟（时戳不可被应用层篡改） | D1 送达回执的"停留时长"入证明对象（§4.7.1 安全时间源路径）；无此能力位的时长字段为 claimed（不参与证明） |

（其余能力位——传感器锚定、显示通道确认等——留待后续版本；能力位声明同受虚标禁令约束。）

### 5.2 LoA 表 = min(设备机制上限, 场景要求)

| LoA | 名称 | 机制要求 | 证据产出 |
| --- | --- | --- | --- |
| L0 | 通知 | 任意 | 无 |
| L1 | 知情确认 | 软件确认；**语音应答仅辅助信号，不得单独构成**；作为辅助信号的语音**禁止留存音频原文**（声纹属敏感个人信息，个保法 §28——审计层仅记录判定结果或其 hash） | 软件日志 |
| L1.5 | 物理确认（受限） | 物理按键 + challenge 绑定签名（DCC-C 为应用自证）；**DCC-B/C 的机制上限**（B 可 `attested_by: "device"`，C 仅 `attested_by: "app"`） | 物理事件签名 + 披露 hash 绑定 |
| L2 | 高保障确认 | 物理事件 + **DCC-A** + 时序绑定 + 呈现承诺合规 | 判责链四段完整 |
| L3 | 增强确认 | L2 + CA 认证式电子签名 + TSA 时间戳 + 第三方托管（**目标构成，非现状**） | 金融级（Enterprise Profile，规划中；Core v2.0 未定义该轨道，见 §9.1） |

- **物理按键本身不产生 LoA；产生 LoA 的是"物理事件 + 密钥机制"的组合。LoA 是属性不是标签。**
- 语音独立确认禁止的依据：5 秒语音样本即可克隆声纹（2026 实证 [S20]）。
- L3 保留给 Enterprise Profile；IG-Lite 的最高目标等级为 L2。
- 编号说明：本表 L0–L3 为保障等级编号，与 Core 四层架构编号（激活层/物理动作层/凭证层/审计层，Layer 0–3）**无对应关系**（§2 编号消歧）。

### 5.3 静默降级禁令

Grant **必须**声明 `loa_target`；运行时实际 LoA 低于 `loa_target` 时，Agent **必须**重新请求（重新披露 + 重新确认）或放弃执行。**静默降级 = Grant 无效。** 同构规则（v0.2）：Disclosure Object 声明 `delivery_tier` 而实际送达证明低于声明（如 D2 声明降级为 D0 渲染留痕），比照静默降级处理——回执缺失或等级不符的披露，验证端按实际等级采信并记审计层。

### 5.4 共享设备约束

多人共用设备（无佩戴检测或共享配对）→ LoA **封顶 L1.5**；佩戴检测 + 单人配对可按 DCC 达标。

理由：耳机是最高频共享品类（家人拿错、儿童把玩），"物理在手 = 本人授权"对其不成立。家庭场景披露模板**应当**注明当前佩戴者身份（尽力而为声明）。

### 5.5 无障碍替代通道

- 确认动作模式（§10.1.1）允许等价替代通道（先例：Apple Pay 侧键确认的 AssistiveTouch / Switch Control 替代 [S9]）。
- 替代通道**必须**在 Grant 的 `confirm_modality` 字段声明并入审计层；**替代是可达性问题，不是降低 LoA 的理由**——若某替代通道机制上弱于标准动作，按其实际机制定级。

### 5.6 送达等级与 LoA × Delivery 组合（v0.2 新增）

**Delivery Tier（D 级）独立于 LoA**，只描述披露送达强度，两轴正交：

| D 级 | 名称 | 机制 | 证明物 | 状态 |
| --- | --- | --- | --- | --- |
| D0 | 渲染留痕（审计级） | §3.3 渲染留痕，渲染方自证 | 播报文本 hash + 音轨 hash | v0.1.1 已有 |
| D1 | 弱表面送达回执 | §4.7.1，DCC-B 以上设备对渲染事实签名 | 设备签名 content_hash（含 nonce） | v0.2 规范定义 |

## 6. 告知基线：Schema Registry（v0.2 新增）

> 本章将 v0.1.1 §10.2「已知限制」中"告知充分性不在域"条目升级为规范机制。设计上游：设计稿《告知基线 Schema Registry》（v0.2，2026-09-16 起草、2026-09-20 原文核验批＋red-team 修订后并入）。

### 6.1 概念模型：告知义务是四个独立要件

| 要件 | 回答的问题 | 承载机制 | 版本状态 |
| --- | --- | --- | --- |
| ① 充分性 | 该说的都说了吗 | **本节 Schema Registry** | v0.2 新增 |
| ② 完整性 | 说的没被改吗 | disclosure_hash + 签名 + 托管锚定 | v0.1.1 核心 |
| ③ 送达性 | 说的被看到了吗（给了显著查看机会） | D0 渲染留痕（v0.1.1，审计级）→ D1/D2 送达回执（v0.2 §4.7，设备签名级） | v0.2 升级 |
| ④ 意思真实 | 是本人主动同意的吗 | IntentGrant（物理确认） | v0.1.1 核心 |

完整证据链一句话：**该说的都说了、说了的没被改、改不了的确实给了看的机会、看到的被本人授权了。**

要点：四个要件相互独立，缺一环则整链在对应问题上失明。schema 补的是第①环——它不与既有机制竞争，而是让 disclosure_hash 有了"内容下限"：v0.1.1 的 `disclosure_hash` 解决**完整性**（说了的没被改），不解决**充分性**（该说的都说了）——哈希锚定一份不充分的告知，等于给违规披露盖了骑缝章。

### 6.2 Registry 架构与治理

- **形态**：开源 schema 注册表，按交易类型登记类型 schema（§6.4 首发 T-0/T-AIR/T-SUB）。schema 是数据模型（字段、类型、required 集合、N/A 规则）＋法源映射（§6.6），不是代码。
- **版本化**：`ig:disclosure:<类型>@<语义化版本>`；Registry 保留全版本历史（append-only），版本发布走公开评议（与 §13 版本纪律一致）。
- **与 §8 托管方的关系**：Registry 定义"什么是完备披露"，托管方锚定"披露 hash 确实在交易前存在"——Registry 不锚定证据，托管方不解释 schema；两者职责分离。
- **准入审计**：厂商接入 Registry 的准入审计与 §8 托管准入共用机制（审计频率、降级标记、公开问责）。N/A 滥用抽查同用此通道（§6.3）。
- **开源治理**：schema 定义文件随本规范同仓发布（Apache 2.0）；外部提交新类型 schema 走 PR 评议——**新类型必须完成法源映射方可合并**（无公开法源的类型只能以 recommended 级登记）。

### 6.3 强制力链与生态定位

**强制力链（四环，环环独立）**：

1. **签发端**：PAE SDK / 控制端应用生成 Disclosure Object 时按 `schema_ref` 校验 required 字段——**缺失、空串、仅空白 → 拒绝生成 challenge**（交易在协议层走不到确认环节，§4.2 签发前置校验、§4.4 `rejected_schema` 态）。
2. **哈希端**：全部字段（required 与 vendor 一并）参与 canonical serialization（RFC 8785 JCS）与 `disclosure_hash` 计算——事后任何改动都会使 hash 验证失败，与 v0.1.1 防篡改机制同一强度。**分工必须分清**：hash 保证的是**完整性**（验证端看到的披露＝签发时的披露，对任意字段一视同仁）；**完备性校验由第 3 环的 schema_ref 复算承担**——hash 本身不判断"该有的字段没填"，两条机制不得互相冒名。
3. **验证端**：审计层与托管方验证时，`schema_ref` 版本仲裁（§6.5）后复算 required 完备性——**结构不合规的 Grant 直接判 invalid，不进入"证据效力强弱"讨论**。
4. **法律端**：协议层拒签只是机制；真实的强制力是披露不合规本身的法律后果（《消保条例》法律责任章、格式条款不订入合同、典型案例确立的赔偿规则 [S46][S47]）。协议把法律后果变成工程后果——这是"翻译"而非"发明"。

> **生态定位诚实边界（red-team L-2 修订）**：签发端校验防的是**无意不合规**（开发者漏字段），防不了有意绕过（不经 SDK 自拼凭证）——它是**质量过滤器**，不是准入拦截。自愿生态里真正的牙齿在验证端仲裁与法律端：结构不合规的凭证判 invalid、不合规披露依法丧失证据效力——那是事后仲裁，依赖法院与托管方买账。两层各防一类对象，不得混称"协议层拦截"。

**N/A 显式声明规则**：不适用某 required 字段时，必须显式声明 `"applicability": "not_applicable"` **并附判定理由**（引用真实法理，见 §6.4 T-0 示例），禁止静默省略、空串、`null` 三态。滥用 not_applicable（显易不适用的场景声称豁免）由托管方准入审计抽查（§6.2），查实后该厂商后续交易凭证降级标记。**《消保条例》§19"不得擅自扩大不适用无理由退货的商品范围"构成 N/A 真实性的反向法源锚——N/A 理由必须真实，虚构豁免即"擅自扩大"。**

**Vendor Namespace（add-only）**：厂商可扩展自有字段（`vendor.examplecorp.*`），**只能加、不能覆盖 required**；vendor 字段参与 hash（防事后改写）但 schema 校验只对 required 生效。方向：让厂商披露"超出基线"成为可对比、可宣传的差异化（把披露充分性变成正面竞争维度，而非合规负担）。**真实性边界**：vendor 字段由厂商自证＋准入审计抽查，非协议担保——跨厂商对比仅在同一 Registry 治理下的经审计厂商间成立，防止营销滥用。

```json
  "required": {

```

### 6.5 版本化与取证仲裁

`schema_ref`（含版本号）作为 Disclosure Object 核心字段入 hash。争议取证时按**交易发生时点适用的 schema 版本**判定完备性——法源修订后新版本不溯及既往。Registry 保留全版本历史，托管日志可交叉验证版本真实性。

**T-SUB 跨版本切换**：续扣按**扣款时点**适用的 schema 版本复算——提前 5 日提醒是每次扣款前的新义务，单次交易时点规则对订阅不足，故续扣凭证独立校验。法源修订触发版本升级时：存量订阅不溯及重披露，但升级生效后产生的续扣凭证按新版本复算完备性；N 日评估窗口内旧版生成的凭证效力维持，评估窗口本身作为诚实边界声明（应知新法与机制升级之间的时滞由 N 日机制承担）。

**N 日评估机制**：法源修订后，Registry **应当**在 30 日内（默认值，可由治理决议调整）完成受影响 schema 的评估与版本发布；该窗口是"法源已变、schema 未及跟进"期间的诚实边界，窗口内旧版凭证效力维持（§6.5 不溯及原则），窗口超期未评估的事实由 Registry 公开状态页披露。

### 6.6 法源映射与核验状态

**规则（对应 §1.4 原则六）**：schema 每条 required 字段**必须**挂法源引用——条文号＋施行日期＋生效状态；无公开法源支撑的字段不得进 required（可入 recommended）；判例引用写发布主体＋日期，不编案号。

**核验分级（2026-09-20 原文核验批，详见 research/v02-factcheck-法源核验-2026-09-20.md）**：

- **官方多源逐字确认（≥3 官方/权威源交叉）**：《消保条例》第十条 [S55]；《网络交易监督管理办法》§18 [S56]；《电商法》§17 [S48]；《消保法》§20/§21/§25 [S49]；《消保条例》§19 [S50]；民航 2018 通知（caac.gov.cn 官网页，文号局发明电〔2018〕1952号）[S52]；最高法 2026-03-15 消保典型案例案例1（court.gov.cn/新华社/人民网）[S47]；广州互联网法院 2025-08 全额退款案（人民日报 2025-08-07 以案说法＋司法部智慧普法平台）[S46]。

## 7. PAE：术语、能力声明与发现

### 7.1 术语对齐 FIDO

刻意差异：CTAP2.3 允许单次触摸构成 UP [S6]；IG-Lite 捕获**同意信号**，单击不构成同意（§10.1.1）。两者安全目标不同（在场 vs 同意），差异是设计选择不是疏漏。

### 7.2 能力声明（Capability Descriptor）

PAE **必须**向控制端应用提供能力声明（GATT 读取或配对注册信息）：

```json
{
  "pae_id": "PAE-2026-0001",
  "core_version": "2.0",
  "profile": "ig-lite",
  "profile_version": "0.2",
  "dcc_class": "B",
  "fw_version": "1.2.3",
  "confirm_modalities": ["double_click", "long_press"],
  "uv_available": false,
  "display": { "type": "none" },
  "pairing_models": ["numeric_comparison", "just_works"],
  "capability_flags": {"secure_clock": false},
  "battery_percent": 90
}
```

**诚实声明纪律**：`dcc_class`、`confirm_modalities`、`uv_available`、`capability_flags` 与实际机制不符，即构成虚标——该设备的全部历史 Grant 证据力按实际机制降级判定（第 12 章）。

能力广告与绑定事实的区分：`pairing_models` 声明设备**支持**哪些关联模型；实际绑定所用的模型以 激活层绑定记录的 `association_model` 为准（§3.5）——LoA 封顶判定依据后者，不依据能力声明。

### 7.3 发现与确认请求路由

- **本地发现**：BLE 广播与 GATT 沿用 Core v2.0 第 5 章（Service/Characteristic UUID、6 字节事件包）；本规范不重定义。
- **注册表**：控制端应用维护已配对 PAE 注册表（含能力声明快照与 激活层绑定事实：`association_model`（§3.5）、绑定时间、复核状态）。
- **路由规则**：Agent 任务进入 A2A auth-required（或本规范定义的 confirm-required 等价状态）→ AIOS 查询注册表 → 按 §5.4 共享约束与场景默认 PAE 路由 → 无可用 PAE 时按 §5.3 处理（重新请求或放弃），**禁止**静默退化为纯软件确认后仍宣称原 `loa_target`。
- **跨设备/跨生态云注册**：后续版本可选（未来工作，第 12 章）。

### 7.4 绑定与复核

- Core v2.0 第 4 章（激活层流程、绑定字段、锁定与冻结策略）在消费者语境由控制端应用执行；管理员复核路径替换为 §3.5 绑定后人工复核。
- 挂失与撤销对齐 Core 第 10 章：控制端一键挂失 → `Bind_Status` 冻结 → 该 `pae_id` 全部未过期 Grant 强制撤销。
- 消费者语境的简化声明：Core 的岗位上下文交接（第 11 章）不在本 Profile 范围。

## 8. 证据托管

> 本章为 Core v2.0 第 7 章（审计层）的 Consumer 替换：企业侧存储 → 中立托管 hash 日志。

- **独立性依据（披露 hash 为何必须外部锚定）**：判责链四段（§3.4）中，确认段由 PAE 侧密钥签名（§3.5）、执行段有 Receipt 对齐（§4.5），两段记录的生成方与利害关系方可分离；**披露段则生成方与利害关系方同体**——Disclosure Object 由 Agent/平台生成并呈现（§3.1/§3.2），若其留存与证明亦由呈现方单方承担，争议时构成自证：用户主张"未被如实告知"，平台以自己生成并持有的日志自证已告知。依《最高人民法院关于民事诉讼证据的若干规定》§93 [S30]，电子数据真实性审查落在生成/存储所依赖系统环境的完整性上，而该环境由利害关系方控制；《人民法院在线诉讼规则》§16"上链后推定真实、上链前另行审查" [S31] 恰使单方生成环节成为审查薄弱点。故披露 hash 的中立外部锚定不是增值功能，而是该字段在争议场景下证据效力的成立条件——此为本章独立性要求与 §3.4 四段禁合并的证据法共同根据。**v0.2 延伸**：D2 源披露留痕（§4.7.2）的采信级主张以完整托管路径为前提——同一论证覆盖中转链路的源哈希锚定。
- **定位收窄**：托管方 = CT 式 append-only hash 日志运营方，仅做"准入 + 公开审计"，**不存原文、不做时间戳权威、不做判责**。
- **时间戳**：叠加 RFC 3161 TSA [S13]，优先国内司法认证服务（如联合信任时间戳 tsa.cn [S16]）——TSA 是组件供应商不是竞品。
- **独立性**：托管体系**必须**由 ≥2 家独立运营方互备（CT 多日志 + gossip 模式 [S14]）；托管方与平台/设备/OS 方的利益关系**必须**公开声明。试点期允许单日志先行，但该降级状态**必须**写入托管方公开声明（与 §12 实现状态声明的分级一致）。
- **准入审计**：参考 CT inclusion proof 模式 [S14]，第三方可验证"某 hash 确已被托管"；托管方拒绝准入 = 可被外部发现。
- **托管日志内容下限**：仅收录 hash 与时间戳，**禁止**收录 `do_id`、per-receipt nonce 与任何原文要素——`do_id` 只存在于争议对峙双方的原文副本中；nonce 与渲染内容的对应关系同样禁止收录（§4.7.1 隐私红线）。这是"公开日志可审计、原文不可枚举重建"的熵前提（§3.1、§4.7.1；威胁模型见 §11.1）。**v0.2 扩展（C.8 采纳）**：送达回执 hash（D1 `content_hash`／D2 `rendered_content_hash` 的最终值）**应当**入托管日志（回执哈希入托管）——其熵前提与 §3.1 同款：计算输入含高熵 `receipt_id`（UUID）与 per-receipt nonce，低熵披露经双重高熵注入后字典枚举不可行。
- **资质路线**：试点托管 hash（非个人数据）无资质门槛；争议冻结证据包可随时送公证/司法鉴定升级效力。
- **不可偷改的架构依据**：托管方可信度不靠运营方自律，靠 CT 式 append-only + inclusion proof + gossip 的三方可验证结构——这是"去信任化托管"的关键表述 [S14]。

## 9. 法律效力与证据规则（中国法锚点）

### 9.1 电子签名双轨制

- **IG-Lite 轨道（Lite = 客服判责级）**：《电子签名法》§13 第二款——"当事人也可以选择使用符合其约定的可靠条件的电子签名" [S27]。采用 IG-Lite 的平台**应当**在用户协议中援引本款，将本规范的证据规则约定为"约定的可靠条件"（并以 `evidence_rules_version` 锁定版本，§3.1）。CA 认证不是可靠性前提（《电子签名法》§16：第三方认证是可选服务）。
- **Core v2.0 现行文本**：端点私钥签名（量产设计由 SE 芯片片内完成，Core 第 12 章），**未定义** CA 认证式电子签名的效力路径。《电子签名法》框架下的 CA 认证轨道（§13 第一款；第三方认证属 §16 可选服务）留待金融级 Profile 扩展定义——在此之前，金融级场景的效力论证**不存在可引用的 Core 章节**，不得以"见 Core"指引读者。
- 《电子签名法》§14：可靠电子签名与手写签名/盖章同等效力 [S27]。
- **格式条款防御（R-19）**：用户协议援引属于**格式条款**。依《民法典》§496 第二款，提供格式条款一方未履行提示或说明义务、致使对方没有注意或理解与其有重大利害关系的条款的，对方可以主张该条款不成为合同内容 [S40]。故约定式轨道要求：
  1. 约定条款（§13 第二款援引 + 证据规则版本）**必须**以显著方式提示——单独页面呈现或加粗标识 + 独立确认动作，不得埋于长协议尾部；
  2. 该提示-确认动作本身**必须**入审计层——"提示发生过"的证据亦由本规范证据链承载（协议为自己的法律地基出证）；
  3. 效力归属声明：平台未履行提示义务所致的约定效力瑕疵，由平台自行承担；本规范证据链不补偿该瑕疵。

### 9.3 留存分层（N 参数）

机制 + 下限由本规范定义；具体值由行业 Profile 调参并以 `evidence_rules_version` 锁定。

| 场景 | 披露原文 N 默认 | 下限依据 |
| --- | --- | --- |
| 通用消费确认 | 90 天 | 平台客服判责窗口 |
| 耐用消费品 / 三包类 | ≥ 三包有效期（典型 1–2 年） | 三包争议期覆盖 |
| 金融类确认 | ≥ 行业法定留存期 | 监管要求决定，规范不代拍数字 |

| 证据层 | 留存 | 依据 |
| --- | --- | --- |
| hash + 签名链 | 永久（非个人数据） | hash 为单向摘要，且计算对象含 ≥128bit 随机 `do_id`（§3.1）——低熵内容经高熵注入后字典枚举计算不可行；个保法 §4 第一款明定个人信息**不包括匿名化处理后的信息**（匿名化定义见 §73(四)）——「不可识别信息不属于个人信息」的法理主锚。v0.2 同款论证扩展至送达回执 hash（计算输入含高熵 `receipt_id` 与 per-receipt nonce，§4.7.1/§8） |
| 审计层日志 | ≥6 个月（审计索引与控制端本地完整性 hash 链等机制数据——此链为审计层自身的完整性链，非 §8 托管方 hash 日志，后者永久，见上行） | 网安法 §21；其中披露原文部分（渲染留痕）受本节 N 参数约束，N 到期后仅存其 hash（§3.3） |
| 平台交易信息 | ≥3 年 | 电商法 §31 |

**披露原文的存储责任方**：平台侧（订单记录，电商法 §31）与用户侧（Grant 副本含披露快照）为主要责任方；AIOS/控制端应用的披露副本与渲染留痕留存**应当** ≤N，到期仅存 hash。删除请求（个保法 §47）到达时，控制端应用删除的是原文与渲染留痕——hash 链不受影响。

**司法场景的证据重构（R-18）**：披露原文 N 日过期的设计依据是**客服判责窗口**，不是诉讼时效——普通民事诉讼时效为三年（《民法典》§188 [S39]）。超出 N 窗口的司法争议按以下路径重构证据，本规范明示此取舍：

1. 托管方原文已过期销毁，但 hash 链**永久留存**；
2. 争议时由**持有原文的一方**出示内容（平台订单记录受电商法 §31 三年留存约束；用户侧 Grant 副本含披露快照），计算其 hash 与托管链上的 `disclosure_hash` 对齐——一致即证明"当时披露的内容与今日出示的一致"，此即"hash 先行、原文后验"（hash now, reveal later）架构；
3. 若平台侧亦无原文或对齐失败，按证据规则由负举证责任的一方承担不利后果（方向与最高法银行卡司法解释一致：主张授权交易者举证 [S34]）——举证压力压给记录的控制方，而非消费者。

### 9.4 争议冻结（"停止处理"语义）

任一方向平台争议流程提交主张且托管日志收到冻结请求 → 披露原始片段进入**停止处理态**（个保法 §47 第三段语义 [S32]）：除司法/仲裁调用外不可访问；冻结局内不适用 N 过期；冻结事件本身入审计层。

**这不是法外留痕，是法内停用**——留痕的是 hash（非个人数据），原文在冻结期间仅存储与安全保护、不作任何目的使用。

## 10. 场景与设计约束

### 10.1 确认经济性（Anti-Fatigue）

> 本节是 IG-Lite 的地基条款：**整套协议的价值建立在"确认有意义"之上**。确认若无频率与内容成本控制，等同于攻击面（Uber 2022 MFA 疲劳攻陷、cookie 横幅 72% 无视，实证见 10.1.4）。

#### 10.1.1 确认动作模式（Consent Action Pattern）

有效同意信号**必须**为以下模式之一，**单击不构成同意信号**：

- **双击**：两击间隔 ≤600ms（默认值，行业 Profile 可收紧；Core v2.0 §5.5 固件阈值为 ≤350ms，行业 Profile 可收紧对齐）；
- **长按**：持续 ≥800ms（默认值，对齐 Core v2.0 第 5.5 节固件识别）；
- 声明式等价替代（无障碍等，§5.5）。

**先例坐标系（在场信号 vs 同意信号）**：

| 信号类型 | 先例 | 动作 | 防什么 |
| --- | --- | --- | --- |
| 在场（presence） | FIDO CTAP2.3 UP [S6] | 单次触摸 | 恶意软件静默签名 |
| 同意（consent） | Apple Pay 侧键确认 [S8][S9]、Ledger 双键并按 [S10] | 双击/双键 | 误触 + 疲劳性无意识确认 |
| 同意（consent） | Microsoft Authenticator number matching [S23] | 输入映射数字 | 疲劳轰炸（Uber 2022 类攻击 [S21]） |

IG-Lite 捕获的是**同意**，故动作模式**必须**高于在场信号——这是与 FIDO（单触合规）的规范差异依据。弱表面的 number matching 等价物 = §3.2 结构化三元组播报：用户听到的内容本身承载交易要素，按键即对该内容同意。

#### 10.1.2 频控参数（默认值）

- `confirm_per_session` 默认 ≤5（单 Agent 单会话）；超配额 → Agent **必须**申请 Access Grant 常授权或停止请求；
- **元确认豁免**：Access Grant / 降级申请 / 解锁类请求本身的 Confirm Grant **不占** `confirm_per_session` 配额（否则配额耗尽后 Agent 永远无法申请升级，形成死锁）——但元确认仍走完整披露-播报-确认流程并记审计层；
- 配额计数器由控制端应用本地维护并入审计层（防 Agent 侧自欺）；DCC-A/B 设备**应当**在 PAE 设备侧同步计数并经事件签名上报；
- 同 `disclosure_hash` 豁免窗口 T 默认 10 分钟（豁免的语义见 10.1.3）；
- 同一披露 30 秒内重复请求确认 → Agent 违规记审计层。

#### 10.1.3 播报-按键窗口配对

- 披露播报完成后 ≤60 秒内按键有效；播报中按键 = 无效（静默期）；
- **重复披露豁免 = 免重复播报，不免物理确认**：同 `disclosure_hash` 在 T 窗口内被再次请求确认时，Agent **可以**省略重复播报，但用户的物理确认动作（§10.1.1）**不可省略**，且审计层**必须**记录"豁免播报的确认"（可追溯，不可抵赖不减）。理由：豁免省的是"内容重复呈现成本"，同意信号本身若可豁免，则等于绕过 §4.3 的 Access Grant 签发流程获得常授权效果，频控体系被架空；
- 违规后果：确认疲劳行为入 Agent 信誉（后续版本字段，v0.2 预留）。

#### 10.1.4 设计依据（实证锚点，信息性）

- **MFA 疲劳真实攻陷**：Uber 2022-09，攻击者连续轰炸 MFA push + 冒充 IT 支持话术，承包商最终批准致全局沦陷 [S21]；Akira 勒索团伙 2025 年仍在使用同手法 [S22]——确认若无频率与内容成本控制，等同于攻击面。
- **Consent 疲劳量化**：72% 用户无视或随机点击 cookie 横幅（Flowconsent 2026）[S24]；约 2/3 用户行为不随横幅设计改变（CookieYes）[S25]；平均停留约 7 秒（转引 [S26]）——高频 + 同质 + 无内容映射成本的确认 = 无人确认。
- **结论性设计命题**：**确认的价值密度 = 确认频率⁻¹ × 内容映射成本**。IG-Lite 同时从两端控制：频控（10.1.2）+ 内容映射（§3.2 三元组）与注意力绑定（§3.2 跨面尾码）+ 动作模式成本（10.1.1）。

### 10.3 先例引用（"非激进创新"论证，信息性）

- **LoA × 额度分层**：银联双免（单笔限额 + 风险全额赔付）、央行 Ⅲ 类账户（余额上限隔离风险敞口）、数字人民币无电支付（免密额度内直扣、超限密码）[S36][S37]——金融体系 20 年从未接受"无确认/全确认"二选一，而是"额度 × 确认方式 × 赔付兜底"三层设计。IG-Lite 把这套逻辑协议化并扩展到非支付场景。
- **物理确认**：Apple Pay 侧键双击 [S8]（消费级用户教育已完成——"物理按键 = 我在确认"的习惯迁移成本 ≈0）；硬件钱包 WYSIWYS [S10][S11]。
- **配对开窗**：Matter commissioning 物理动作开窗 [S12]（IoT 反劫持通行模式，硬件厂商即懂）。
- **披露义务机读化**：《网络交易监督管理办法》§18 的"前五日显著提醒"本身就是监管对提醒时点的程序化 [S56]；民航阶梯费率公示是监管对披露结构的表格式要求 [S52]——schema 把监管已有的"程序化披露"传统延伸到机器可验证层（§6.6）。
- 判责侧的金融与平台先例详见配套文档《判责经济学（一页）》。

## 11. 安全考量与已知限制

### 11.1 威胁模型汇总（攻击向量 × 缓解 × 残余风险）

| 攻击向量 | 缓解条款 | 残余风险（诚实边界） |
| --- | --- | --- |
| 披露内容与签署内容不符（尾码碰撞/播报内容偷换） | 呈现承诺强制格式：跨面尾码核对（须第二可信面）或结构化三元组；禁止单面裸尾码（§3.2） | a) 尾 8 位抗碰撞 32bit、GPU 枚举分钟级可行——前提为第二呈现面与 challenge 签发方不同时沦陷；第二面与签发方同体（如以控制端应用屏幕为第二面）时，尾码仅保留注意力绑定语义，不构成对该方的完整性校验；内容完整性由 审计层渲染留痕与核心字段一致性比对事后检出（VIOLATED） |
| 披露 hash 字典枚举（公开托管日志重建交易内容） | `do_id` ≥128bit 随机纳入 hash 计算；托管方禁录 do_id（§3.1/§8） | 无（计算上不可行） |

### 11.2 已知限制

- **胁迫按键未覆盖**：物理在手 ≠ 自由意志；本规范不设胁迫信号（银行亦无普遍方案），后续版本预留双长按胁迫标志。
- **离线场景不可用**：确认依赖实时 challenge；离线按键丢弃（缓存转发 + 降级标记为后续版本议题）。
- **音频侧签署级绑定未覆盖**：音频证据止于审计级（§3.3 渲染留痕：音轨 hash 留痕播报事实，文本 hash 承担一致性比对）；将规范化播报稿纳入 Grant 签名对象需先定义 TTS 规范化对象与引擎配合要求——后续版本议题。
- **~~告知充分性（Adequacy）不在域~~ → v0.2 已闭合（§6）**：告知基线 Schema Registry 按交易类型将现行法律披露义务机读化，required 字段经签发端校验（拒签）与验证端复算（判 invalid）双重强制，法源映射与核验状态见 §6.6。**保留限制**：①Registry 覆盖以已登记类型为限（首发 T-0/T-AIR/T-SUB，未登记交易类型回落 T-0 或无 schema 状态）；②schema 滞后于法源修订的过渡窗口（§6.5/§11.1）；③`dispute_entry` 等无公开法源字段仅 recommended 级（§6.4.0）。
- **~~送达性止于审计级~~ → v0.2 部分闭合（§4.7/§5.6）**：D1/D2 设备签名送达回执将"存储 ≠ 显示"攻击的证明链从平台自证（D0）升级为设备签名级。**保留限制**：①DCC-C 端点无设备签名能力，送达证明仍为 D0 审计级（§4.7.1）；②无安全时钟端点的停留时长为 claimed 字段不可证明（§4.7.1）；③D2 源披露留痕依赖源平台商务配合，未对接前 D2 不可得（§4.7.3）；④仅时间戳路径的回执限审计参考（§4.7.2）。**送达回执不承载同意语义**：同意唯一由 IntentGrant 承载，回执中的任何用户动作均不构成 §10.1.1 意义上的同意信号。
- **DCC-C 封顶 L1.5**：诚实标注，给供应链"过了 DCC-B/A 才能进 L2"的升级阶梯，而非虚标。
- **监控悖论**：本协议新增个人信息 ≈0（hash 非个人数据 + 原文 N 天 + 停止处理机制，个保法 §47）——见 §9.3/§9.4。v0.2 送达回执与 nonce 遵守同一论证（§8 托管禁录条款）。
- **披露模板公平性不在协议域**：渲染文本是否构成误导性表述（dark pattern）属平台治理与消费者保护审查问题；本协议只保证"当时呈现了什么"可被事后证明。**v0.2 边界澄清**：schema 的 required 字段规定"该说的说了"（信息集完备），不审查"说的方式是否误导"——两者互补不重叠。
- **未成年人场景未覆盖**：PAE 持有者可为限制民事行为能力人（《民法典》§19）；§5.4 共享封顶压缩 LoA，但不解决行为能力归属——后续版本考虑 UV/年龄门槛（监护人委托链为 v2.1 候选，不进本版）。
- **mandate_ref 单向引用**：AP2 生态不识别 IG-Lite；语义兼容、字段可映射，不宣称互操作。
- **标准政治风险**：FIDO AA TWG 若发布冲突的捕获保障规范 → 生态分裂风险；本规范的应对是术语对齐（不对抗）+ 中国法锚点 + 弱表面场景的差异化定位，并向 TWG 提交评论意见（未来工作）。

### 13.1 演进路线与公开实现

**v0.2 已采纳（自 IG-MCP 附录 C 八条提案）**：C.1（送达性→§4.7 D1/D2 与 §5.6 送达等级）为 v0.2 主线之一；C.8（回执哈希入托管日志→§8）已采纳并同步声明熵前提（计算输入含高熵 `receipt_id` 与 per-receipt nonce，与 §3.1 `do_id` 同款论证）。C.2/C.3/C.4/C.5 的语义由 §4.7/§5.6/§3.1 的 v0.2 结构吸收或替代（`delivery_tier` 字段取代 C.5 的场景表加列方案）；C.6（无可用 PAE 显式错误码）/C.7（对齐容差锁定）为后续版本议题。

**后续版本候选**：presence_mode（0x01 本地 BLE＋邻近性/0x02 远程/0x03 远程＋位置证明）与委托链（delegation chain）为 **v2.1 候选**（2026-09-17 登记，凭证字段扩展）；缓存转发、UWB 测距、TTS 规范化对象、胁迫标志、UV/年龄门槛、C.6/C.7 同批评审。

**公开实现**（实现状态详见 §12）：

- **IG-MCP 接口定义 v0.1**：MCP 工具层语义（confirm-required 状态的接口化），双形态（HTTP 主形态＋stdio 辅形态）、三角色鉴权模型、Resources 资源面。独立文档，不并入本规范（传输层中立纪律，§2.4）。
- **ProofMesh origin-api v0.3**：链路原点服务的线上实现（Confirm Grant 签发/查询/消费/状态机四态，Ed25519＋RFC 8785 JCS＋TTL 一次一用），公开可独立复核（公钥与验签材料随凭证自包含分发）。其演示密钥由固定种子派生（key_is_demo 公开声明），生产实现必须更换密钥管理（HSM/KMS）并如实披露。
- **诚实边界（与配套演示系统统一陈述）**：本规范及其实现可检验的部分是**可复算**（被签名字节、披露 hash、签名三者的独立验证），不是**被采纳**（尚未提交任何标准组织、无第三方实现）；T2（防事前造假）依赖独立第三方披露来源，尚未达标——本规范 §8 的中立托管要求即为此预留。

## 附录 B：参考实现形态（DCC-C）

**形态**：市售通用蓝牙相机遥控按键（此类设备无安全边界、无固件级密钥、事件经 BLE HID/Notify 上报）+ 控制端应用。

**能力事实**：签名实际发生在控制端应用（`attested_by: "app"`）；按 §5.2 机制条件化，此类实现**封顶 L1.5**。这一定级同时给出供应链升级阶梯：DCC-B（固件密钥+设备端签名）→ L1.5 证据可标 `attested_by: "device"`，且可承载 D1 送达回执（§4.7.1，无 `secure_clock` 能力位时时长字段为 claimed）；DCC-A（SE/TEE）→ 可达 L2。

**发布物**：随 v0.1 附开源最小参考实现（伪代码级）——配套文件《IG-Lite 参考实现-伪代码》，覆盖 Disclosure Object 构造 → 播报 → challenge 签发 → 双击事件 → Grant 签发 → Receipt 对齐的最小闭环；随 v0.2 扩展 required fail 分支、送达回执生成与 fidelity 校验（§12 实现状态）。密码学原语全部委托平台库，诚实边界与 §12 一致。
